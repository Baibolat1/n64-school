# План проекта: закрытый сайт для учеников школы

Внутренний, непубличный сайт школы на **FastAPI + SQLite**. Ученик входит по одноразовому
коду приглашения, получает псевдоним и общается в ленте анонимно для остальных, а также
оставляет структурированные отзывы об учителях по критериям.

## Как запускать

```bash
cd /workspaces/aiogram-bot

# 1. окружение (Python 3.11+, проверено на 3.14)
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2. настройки: скопировать и заполнить
cp .env.example .env
#    обязательно задать SECRET_KEY — он подписывает cookie ученика
#    и служит ключом для хэшей кодов приглашения

# 3. схема БД
.venv/bin/alembic upgrade head

# 4. первый админ
ADMIN_USERNAME=director ADMIN_PASSWORD='длинный-пароль-от-12-символов' \
  .venv/bin/python scripts/seed_admin.py

# 5. запуск
.venv/bin/uvicorn app.main:app --reload
```

Точки входа: `/health` (проверка живости), `/login` (вход ученика по коду),
`/admin/login` (вход админа), `/feed` (лента), `/me` (профиль и смена псевдонима).

Дальше по циклу: админ входит в `/admin/login` → `/admin/invites` создаёт код →
код показывается **один раз** (в БД хранится только хэш) → ученик вводит его на `/login`.

`.env` и `school.db` в git не попадают (см. `.gitignore`); в репозиторий идут только
`.env.example` и миграции.

## Принятые решения

Закрытые вопросы, по которым есть явный выбор (не пересматривать без причины):

| Тема | Решение |
|---|---|
| Фронтенд | Серверные Jinja2-шаблоны, без SPA. API-слой не выделяем |
| Видимость личности | Админ видит связь «контент → ученик»; ученики видят только псевдоним |
| Фильтр ПДн | Жёсткий блок: телефон, email, ссылки, мессенджеры. Мягкая замена на плейсхолдер: ФИО, адрес, номер класса |
| Мягко-помеченный контент | Публикуется сразу, на месте фрагмента — плейсхолдер `[скрыто]`, запись уходит модератору в очередь. Не удерживается |
| Статус `pending` у постов | Не используется. Мягко-помеченный контент виден сразу с плейсхолдером, а модератору уходит запись в очередь `pii_flags` |
| Данные учителей и критериев | В git — только демо-данные с **выдуманными** именами. Настоящие ФИО и критерии приходят из файла вне репозитория (см. «Данные учителей и критериев») |
| Отзывы об учителях | Постмодерация: видны сразу, убираются по жалобе. Премодерации нет |
| Псевдоним | Постоянный по умолчанию + галочка «опубликовать анонимно» на пост. В контенте хранится снимок ника (`display_alias`), смена ника историю не переписывает. Смена — не чаще раза в `ALIAS_CHANGE_COOLDOWN_DAYS` (30 дней) |
| Сессия ученика | Подписанная cookie (`itsdangerous`), таблицы сессий нет. Серверный отзыв невозможен; бан проверяется по БД на каждом запросе |
| Сессия админа | Серверные сессии в `admin_sessions`, в БД — только SHA-256 хэш токена, отзыв через logout |
| Пароли админа | argon2 (`argon2-cffi`), первый админ — скриптом `scripts/seed_admin.py` |
| Коды приглашения | Одноразовые, 12 символов (60 бит), в БД — HMAC-SHA256 от кода с ключом `SECRET_KEY` |
| Rate limit | Счётчики в памяти процесса (один инстанс). При росте нагрузки — таблица |
| Отложено осознанно | Загрузка изображений, личные сообщения между учениками, 2FA для админа, email у учеников, хранение IP |

Следствия для безопасности, о которых надо помнить:

- Контент виден только с валидной сессией; поисковая индексация запрещается на этапе 13.
- Забаненный ученик получает `403` и не читает и не пишет — проверка идёт по БД, а не по cookie.
- Ученик несовершеннолетний: реальные имена, адреса и контакты не должны попадать в публичный текст — этим занимается фильтр ПДн.
- `COOKIE_SECURE=false` в разработке; за HTTPS включается `true` (этап 13).

## Этапы

| № | Этап | Объём | Статус |
|---|---|---|---|
| 0 | Каркас проекта и конфиг: `app/main.py`, `/health`, `config.py`, `db/base.py`, Alembic | S | ✅ готово |
| 1 | Модели и миграции: 13 таблиц, ревизия `0001_init` | M | ✅ готово |
| 2 | Аутентификация админа: argon2, серверные сессии, формы, `seed_admin.py` | M | ✅ готово |
| 3 | Invite-коды: выдача админом, одноразовый вход, создание ученика | M | ✅ готово |
| 4 | Псевдоним: валидация, запрещённые ники, cooldown (миграция `0002`) | S | ✅ готово |
| 5 | Лента: посты, комментарии, пагинация, страница поста | M | ✅ готово |
| 6 | Сервис фильтра ПДн: правила block/flag/pass + 40 тестов | M | ✅ готово |

| 8 | Интеграция фильтра и лимитов в публикацию | S | ⏳ ждёт |
| 9 | Отзывы об учителях: критерии, оценки, один отзыв на пару ученик-учитель | M | ⏳ ждёт |
| 10 | Агрегированная статистика отзывов: средние по критериям, тексты по статусу | S | ⏳ ждёт |
| 11 | Жалобы: причины, защита от повторных, очередь `open` | S | ⏳ ждёт |
| 12 | Админка модерации: очереди жалоб и ПДн, hide/restore/delete/ban, аудит | L | ⏳ ждёт |
| 13 | Харденинг: security-заголовки, CSRF, `noindex`, флаги cookie, лимиты длины, логи без ПДн | M | ⏳ ждёт |
| 14 | Тесты сквозных сценариев, демо-данные, документация | M | ⏳ ждёт |

Каждый этап даёт запускаемый результат: после 3 можно войти, после 5 — писать в ленту,
после 8 — публикация защищена фильтром и лимитами, после 12 — админ модерирует.

### Отклонения от исходного плана

- **Этап 1:** из `invites` удалена колонка `used_by` — она вместе с `students.invite_id`
  давала циклическую зависимость FK, на которой Alembic писал предупреждение. Кто погасил
  код, определяется запросом по `students.invite_id`.
- **Этап 3:** вместо таблицы сессий учеников — подписанная cookie (см. таблицу решений).
- **Этап 4:** добавлена миграция `0002` с колонкой `students.alias_changed_at` — без неё
  негде хранить время последней смены псевдонима, а в cookie лимит не удержать.
- **Этап 8 (план):** мягко-помеченный контент публикуется сразу, а не удерживается в
  `pending`. В `pii_flags` уходит запись для модератора. Статус `pending` у постов не
  используется вовсе (см. таблицу решений).
- **Этап 13 (частично раньше):** CSRF и security-заголовки внедряются вместе с этапами 7–8,
  а не в конце — см. «Порядок работ». Остальное (`noindex`, флаги cookie, лимиты длины,
  логи без ПДн) остаётся в этапе 13.

## Порядок работ

Порядок отличается от нумерации этапов — принят явно, менять без причины не нужно:

1. **Этапы 7 и 8 одним куском**, и в них же — CSRF и security-заголовки (часть этапа 13).
2. **Дизайн-основа** — общий вид, типографика, стили. Отдельная задача, вне таблицы этапов.
3. **Этапы 9–10**, затем **11**, затем **12**, затем **остаток этапа 13** и **этап 14**.

Почему CSRF и заголовки подняты с этапа 13 вперёд: они правят все формы и ответы, написанные
этапами 2–12. Чем позже их внедрять, тем больше переписывать.

## Правило исполнения

| Объём | Этапы | Как делаем |
|---|---|---|
| S | 7, 8, 10, 11 | сам, без субагентов: код, тесты, запуск сайта, проверка руками |
| M | 9, 13, 14 | сам, без субагентов |
| L | 12 | цепочка `planner → coder → reviewer` |

Цепочка субагентов запускается **только** для этапа 12 (L) и для **финальной проверки
безопасности**. Перед запуском цепочки план показывается пользователю, и работа начинается
только после его «ок». В остальных случаях работаю сам, напрямую. Это же правило лежит
в памяти агента.

## Данные учителей и критериев

В git попадают только демо-данные с **выдуманными** именами — для этапа 9 и локальной
разработки. Настоящие ФИО и критерии вносятся отдельно из файла, которого нет в
репозитории (маска `data/*.local.*` в `.gitignore`). Настоящие ФИО учителей — персональные
данные несовершеннолетних-смежного контура, в публичный репозиторий они не идут.

## Что дальше

**Работа остановлена после этапа 6.** Готовы этапы 0–6, каждый проверен вручную на живом
сервере. Дальше — по «Порядку работ», но не раньше команды «поехали»: до неё работа не
начинается.

Следующий кусок — **этапы 7 + 8 + CSRF и security-заголовки**.

Открытые вопросы, которые стоит решить до продакшена:

- нужна ли возможность принудительно разлогинивать ученика (тогда — таблица `student_sessions`);
- включить `COOKIE_SECURE=true` и `SECRET_KEY` из окружения при переходе на HTTPS;
- для этапа 9 сначала идут демо-данные с выдуманными именами; настоящие ФИО и критерии
  подтягиваются из файла вне git — путь согласовать перед стартом этапа 9.

## Заметки о процессе

- Обычные этапы (S и M) делаю сам, напрямую. Цепочка `planner → coder → reviewer`
  (`.claude/agents/`) включается только для этапа 12 и финальной проверки безопасности —
  см. «Правило исполнения».
- Субагенты не делают git-коммитов — коммиты делает человек или основной агент после проверки.
- Каждый этап проверяется вручную на живом сервере: миграции (upgrade/downgrade/`alembic check`),
  доступ без сессии, бан, экранирование HTML, поведение при неверных данных.
