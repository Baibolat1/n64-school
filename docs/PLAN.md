# План проекта: закрытый сайт для учеников школы

Внутренний, непубличный сайт школы на **FastAPI + SQLite**. Ученик входит по одноразовому
коду приглашения, получает псевдоним и общается в ленте анонимно для остальных, а также
оставляет структурированные отзывы об учителях по критериям.

## Как запускать

```bash
cd /workspaces/aiogram-bot

# 1. окружение (Python 3.11+, проверено на 3.14)
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2. настройки: скопировать и заполнить
cp .env.example .env
#    обязательно задать SECRET_KEY — он подписывает cookie ученика
#    и служит ключом для хэшей кодов приглашения

# 3. схема БД
.venv/bin/alembic upgrade head

# 4. первый админ
ADMIN_USERNAME=director ADMIN_PASSWORD='длинный-пароль-от-12-символов' \
  .venv/bin/python scripts/seed_admin.py

# 5. запуск
.venv/bin/uvicorn app.main:app --reload
```

Точки входа: `/health` (проверка живости), `/login` (вход ученика по коду или
по email+паролю), `/register` (открытая регистрация), `/register/qr` (регистрация
по QR), `/scan` (QR-сканер для действующего ученика), `/admin/login` (вход
админа), `/feed` (лента), `/me` (профиль и смена псевдонима).

Дальше по циклу: админ входит в `/admin/login` → `/admin/invites` создаёт код →
код показывается **один раз** (в БД хранится только хэш) → ученик вводит его на `/login`.

`.env` и `school.db` в git не попадают (см. `.gitignore`); в репозиторий идут только
`.env.example` и миграции.

## Принятые решения

Закрытые вопросы, по которым есть явный выбор (не пересматривать без причины):

| Тема | Решение |
|---|---|
| Фронтенд | Серверные Jinja2-шаблоны, без SPA. API-слой не выделяем |
| Видимость личности | Админ видит связь «контент → ученик»; ученики видят только псевдоним |
| Фильтр ПДн | Жёсткий блок: телефон, email, ссылки, мессенджеры. Мягкая замена на плейсхолдер: ФИО, адрес, номер класса |
| Мягко-помеченный контент | Публикуется сразу, на месте фрагмента — плейсхолдер `[скрыто]`, запись уходит модератору в очередь. Не удерживается |
| Статус `pending` у постов | Не используется. Мягко-помеченный контент виден сразу с плейсхолдером, а модератору уходит запись в очередь `pii_flags` |
| Данные учителей и критериев | В git — только демо-данные с **выдуманными** именами. Настоящие ФИО и критерии приходят из файла вне репозитория (см. «Данные учителей и критериев») |
| Отзывы об учителях | Постмодерация: видны сразу, убираются по жалобе. Премодерации нет |
| Псевдоним | Постоянный по умолчанию + галочка «опубликовать анонимно» на пост. В контенте хранится снимок ника (`display_alias`), смена ника историю не переписывает. Смена — не чаще раза в `ALIAS_CHANGE_COOLDOWN_DAYS` (30 дней) |
| Сессия ученика | Подписанная cookie (`itsdangerous`), таблицы сессий нет. Серверный отзыв невозможен; бан проверяется по БД на каждом запросе |
| Сессия админа | Серверные сессии в `admin_sessions`, в БД — только SHA-256 хэш токена, отзыв через logout |
| Пароли админа | argon2 (`argon2-cffi`), первый админ — скриптом `scripts/seed_admin.py` |
| Коды приглашения | Одноразовые, 12 символов (60 бит), в БД — HMAC-SHA256 от кода с ключом `SECRET_KEY`. Остаются **параллельным** способом входа и после порога саморегистрации; у таких учеников нет email/пароля |
| Rate limit | Счётчики в памяти процесса (один инстанс), скользящее окно по ученику. При росте нагрузки — таблица |
| CSRF | Подписанный double-submit: токен в cookie `csrf_token` и в скрытом поле формы. Таблицы токенов нет; проверяется каждый небезопасный метод, включая вход и выход |
| Отклонение при блоке ПДн | Жёсткий блок — отказ, контент не сохраняется. Мягкое срабатывание — текст сохраняется уже с плейсхолдером, в очередь идёт усечённый фрагмент |
| Журнал блокировок ПДн | Отказ по жёсткому правилу пишется в `pii_blocked_attempts`: кто, когда, что публиковал и какие правила сработали. Текста нет вовсе — ни строки, ни фрагмента |
| Что хранится в посте | **Оригинал** автора, в котором заменены только совпавшие фрагменты. Переносы строк и пробелы сохраняются. Нормализация (NFKC, невидимые символы, схлопывание пробелов) нужна только для проверки фильтром |
| Мат и грубые слова | **Разрешены** и в постах, и в псевдонимах: не блокируем и не заменяем. Никаких словарей — модерация только по жалобам |
| Лимит попыток входа | Скользящее окно по IP клиента, тот же ограничитель в памяти. `/admin/login` — жёстко (5 за 15 мин), `/login` — мягко (20 за 15 мин); отказ — `429` + `Retry-After`; успешный вход обнуляет счётчик. IP — только ключ счётчика в памяти, нигде не сохраняется и не логируется |
| Саморегистрация по email+паролю | Открыта, пока всего учеников (инвайтные тоже считаются) меньше `OPEN_REGISTRATION_LIMIT` (30). Порог — общий счётчик за всё время, проверяется в той же транзакции, что и вставка |
| Регистрация по QR | После 30-го — единственный самостоятельный способ входа, кроме инвайта. QR-токен живёт `QR_TOKEN_TTL_HOURS` (24ч), в БД только HMAC-хэш; подтверждает любой действующий ученик. Новый аккаунт получает пароль и сразу сессию |
| Хранение QR-токена у новичка | Серверных сессий нет, поэтому новичок носит свой токен в подписанной cookie `qr_registration` — только для перерисовки/обновления/поллинга страницы; доступа сам по себе он не даёт |
| Отложено осознанно | Загрузка изображений, личные сообщения между учениками, 2FA для админа, хранение IP. (Email у учеников больше не отложен — введён саморегистрацией, см. ниже) |

Следствия для безопасности, о которых надо помнить:

- Контент виден только с валидной сессией; поисковая индексация запрещается на этапе 13.
- Забаненный ученик получает `403` и не читает и не пишет — проверка идёт по БД, а не по cookie.
- Ученик несовершеннолетний: реальные имена, адреса и контакты не должны попадать в публичный текст — этим занимается фильтр ПДн.
- `COOKIE_SECURE=false` в разработке; за HTTPS включается `true` (этап 13).

Каждый этап даёт запускаемый результат: после 3 можно войти, после 5 — писать в ленту,
после 8 — публикация защищена фильтром и лимитами, после 12 — админ модерирует.

### Отклонения от исходного плана

- **Этап 1:** из `invites` удалена колонка `used_by` — она вместе с `students.invite_id`
  давала циклическую зависимость FK, на которой Alembic писал предупреждение. Кто погасил
  код, определяется запросом по `students.invite_id`.
- **Этап 3:** вместо таблицы сессий учеников — подписанная cookie (см. таблицу решений).
- **Этап 4:** добавлена миграция `0002` с колонкой `students.alias_changed_at` — без неё
  негде хранить время последней смены псевдонима, а в cookie лимит не удержать.
- **Этап 8 (план):** мягко-помеченный контент публикуется сразу, а не удерживается в
  `pending`. В `pii_flags` уходит запись для модератора. Статус `pending` у постов не
  используется вовсе (см. таблицу решений).
- **Этап 13 (частично раньше):** CSRF и security-заголовки перенесены в этапы 7–8 и уже
  сделаны — см. «Порядок работ». Остальное (`noindex`, флаги cookie, лимиты длины, логи без
  ПДн) остаётся в этапе 13.
- **Этапы 7–8:** фильтр стоит *после* проверки длины и лимита, поэтому отказ по длине не
  тратит бюджет, а отказ по ПДн — тратит. В БД пишется `clean_text` фильтра — **исходный
  текст автора, в котором заменены только совпавшие фрагменты**, а не нормализованная копия:
  переводы строк и пробелы доходят до базы как есть. Правила при этом работают по
  нормализованной копии (NFKC, вырезание невидимых символов, схлопывание пробелов), так что
  обфускация по-прежнему не пролезает: диапазон совпадения отображается обратно в исходный
  текст по карте позиций (`_normalize_with_map`).
- **Этап 4 (изменено):** проверки мата в псевдонимах нет. Словарь-заглушка удалён, `AliasError.FORBIDDEN`
  больше не существует. Мат разрешён и в никах, и в постах, модерация — по жалобам
  (см. таблицу решений).
- **Миграция `0003`:** таблица `pii_blocked_attempts` для журнала отказов по жёстким правилам
  ПДн. Текста в ней нет ни в каком виде — только ученик, тип контента, коды правил и время.
- **Саморегистрация ученика (вне таблицы этапов):** отдельная задача по auth, выполнена до
  дизайн-основы. Миграция `0004`: колонки `students.email`/`students.password_hash` и таблица
  `registration_qr_tokens`. Первые 30 учеников (общий счётчик за всё время) регистрируются по
  email+паролю, дальше — QR-подтверждение у любого действующего ученика; инвайт-коды остаются
  параллельным путём. QR-картинки генерирует `qrcode`/Pillow на сервере, камеру на фронте
  декодирует вендоренный `static/vendor/jsqr.min.js` (офлайн, без внешних API). Вход
  email+пароль и регистрация ограничены тем же in-memory лимитом по IP. На время до дизайн-этапа
  «Сканер» живёт в верхнем меню — нижняя мобильная навигация появится на дизайн-основе.

## Порядок работ

Порядок отличается от нумерации этапов — принят явно, менять без причины не нужно:

1. ~~**Этапы 7 и 8 одним куском**, и в них же — CSRF и security-заголовки (часть этапа 13).~~ ✅
2. **Дизайн-основа** — общий вид, типографика, стили. Отдельная задача, вне таблицы этапов.
3. **Этапы 9–10**, затем **11**, затем **12**, затем **остаток этапа 13** и **этап 14**.

Почему CSRF и заголовки подняты с этапа 13 вперёд: они правят все формы и ответы, написанные
этапами 2–12. Чем позже их внедрять, тем больше переписывать.

## Правило исполнения

| Объём | Этапы | Как делаем |
|---|---|---|
| S | 7, 8, 10, 11 | сам, без субагентов: код, тесты, запуск сайта, проверка руками |
| M | 9, 13, 14 | сам, без субагентов |
| L | 12 | цепочка `planner → coder → reviewer` |

Цепочка субагентов запускается **только** для этапа 12 (L) и для **финальной проверки
безопасности**. Перед запуском цепочки план показывается пользователю, и работа начинается
только после его «ок». В остальных случаях работаю сам, напрямую. Это же правило лежит
в памяти агента.

## Данные учителей и критериев

В git попадают только демо-данные с **выдуманными** именами — для этапа 9 и локальной
разработки. Настоящие ФИО и критерии вносятся отдельно из файла, которого нет в
репозитории (маска `data/*.local.*` в `.gitignore`). Настоящие ФИО учителей — персональные
данные несовершеннолетних-смежного контура, в публичный репозиторий они не идут.

## Что дальше

**Работа остановлена после этапов 7–8.** Готовы этапы 0–8; часть этапа 13 (CSRF и
security-заголовки) сделана вперёд. Дополнительно (вне таблицы этапов) сделана
саморегистрация ученика — открытая по email+паролю и по QR-подтверждению. Публикация
теперь проходит три ворот: длина, лимит частоты, фильтр ПДн — см. `app/services/feed.py`.
Вход в админку, вход ученика и регистрация ограничены по числу попыток с одного IP
(`app/services/login_throttle.py`).

Следующий шаг по «Порядку работ» — **дизайн-основа**, затем этапы 9–10.

Открытые вопросы, которые стоит решить до продакшена:

- лимиты частоты живут в памяти процесса: при нескольких воркерах нужна таблица;
- за обратным прокси ключом лимита входа становится адрес прокси, пока он не настроен
  пробрасывать реальный (или пока лимит не переедет в таблицу);
- нужна ли возможность принудительно разлогинивать ученика (тогда — таблица `student_sessions`);
- включить `COOKIE_SECURE=true` и `SECRET_KEY` из окружения при переходе на HTTPS;
- QR-сканер использует `getUserMedia`, а он требует secure context: `http://localhost`
  работает в разработке, но в проде `/scan` обязан открываться по HTTPS;
- для этапа 9 сначала идут демо-данные с выдуманными именами; настоящие ФИО и критерии
  подтягиваются из файла вне git — путь согласовать перед стартом этапа 9.

## Заметки о процессе

- Обычные этапы (S и M) делаю сам, напрямую. Цепочка `planner → coder → reviewer`
  (`.claude/agents/`) включается только для этапа 12 и финальной проверки безопасности —
  см. «Правило исполнения».
- Субагенты не делают git-коммитов — коммиты делает человек или основной агент после проверки.
- Каждый этап проверяется вручную на живом сервере: миграции (upgrade/downgrade/`alembic check`),
  доступ без сессии, бан, экранирование HTML, поведение при неверных данных.
- Автотесты — `pytest`; запускать `.venv/bin/python -m pytest tests`. Покрыты фильтр ПДн,
  rate limit, лимит попыток входа, CSRF, security-заголовки и публикация постов с
  комментариями (последние — сквозные, через HTTP и с проверкой строк в БД).
