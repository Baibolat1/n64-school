# План проекта: закрытая соцсеть для учеников одной школы

**Соцсеть для учеников школы**, где **один сайт — ровно одна школа** (см. «Одна школа на
сайт» в таблице решений). Внутренняя, непубличная: контент виден только вошедшим. Ученик
входит по одноразовому коду приглашения или саморегистрацией, получает псевдоним и ведёт
ленту — посты, лайки, комментарии — анонимно для остальных, а также оставляет
структурированные отзывы об учителях по критериям. Стек — **FastAPI + SQLite**.

## Как запускать

```bash
cd /workspaces/aiogram-bot

# 1. окружение (Python 3.11+, проверено на 3.14)
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2. настройки: скопировать и заполнить
cp .env.example .env
#    обязательно задать SECRET_KEY — он подписывает cookie ученика
#    и служит ключом для хэшей кодов приглашения

# 3. схема БД
.venv/bin/alembic upgrade head

# 4. первый админ
ADMIN_USERNAME=baibo@icloud ADMIN_PASSWORD='длинный-пароль-от-12-символов' \
  .venv/bin/python scripts/seed_admin.py

# 5. запуск
.venv/bin/uvicorn app.main:app --reload
```

Точки входа: `/health` (проверка живости), `/login` (вход ученика по коду или
по email+паролю), `/register` (открытая регистрация), `/register/qr` (регистрация
по QR), `/scan` (QR-сканер для действующего ученика), `/admin/login` (вход
админа), `/feed` (лента), `/teachers` и `/teachers/{id}` (учителя и отзывы),
`/report/{target_type}/{target_id}` (жалоба на пост, комментарий или отзыв),
`/me` (профиль и смена псевдонима).

Дальше по циклу: админ входит в `/admin/login` → `/admin/invites` создаёт код →
код показывается **один раз** (в БД хранится только хэш) → ученик вводит его на `/login`.

`.env` и `school.db` в git не попадают (см. `.gitignore`); в репозиторий идут только
`.env.example` и миграции.

## Принятые решения

Закрытые вопросы, по которым есть явный выбор (не пересматривать без причины):

| Тема | Решение |
|---|---|
| Одна школа на сайт | **Мультитенантности нет и не будет.** Один деплой обслуживает ровно одну школу: `school_id` не заводим, данные разных школ в одной базе не живут, выбора школы при входе нет. Ещё одна школа — это ещё один экземпляр сайта: свой `.env`, своя БД, свой первый админ, свои учителя и критерии. Отсюда же следует, что всё «межшкольное» (общая лента, общий рейтинг учителей, кросс-школьные профили) в модель не вписывается |
| Фронтенд | Серверные Jinja2-шаблоны, без SPA. API-слой не выделяем |
| Видимость личности | Админ видит связь «контент → ученик»; ученики видят только псевдоним |
| Фильтр ПДн | Жёсткий блок: телефон, email, ссылки, мессенджеры. Мягкая замена на плейсхолдер: ФИО, адрес, номер класса |
| Мягко-помеченный контент | Публикуется сразу, на месте фрагмента — плейсхолдер `[скрыто]`, запись уходит модератору в очередь. Не удерживается |
| Статус `pending` у постов | Не используется. Мягко-помеченный контент виден сразу с плейсхолдером, а модератору уходит запись в очередь `pii_flags` |
| Данные учителей и критериев | В git — только демо-данные с **выдуманными** именами. Настоящие ФИО и критерии приходят из файла вне репозитория (см. «Данные учителей и критериев») |
| Отзывы об учителях | Постмодерация: видны сразу, убираются по жалобе. Премодерации нет |
| Жалобы | Одна жалоба на пару «ученик + объект», навсегда (уникальный ключ в БД, а не только проверка перед вставкой). Причины — закрытый список кодов (`REPORT_REASON_CODES`), формулировки — в одном месте (`REASON_LABELS` в `app.services.reports`). Жаловаться на свой контент нельзя; скрытый или несуществующий объект отвечает `404` одинаково, чтобы по эндпоинту нельзя было узнавать, что убрал модератор. Первая жалоба ставит статус `open` — очередь этапа 12 |
| Псевдоним | Постоянный по умолчанию + галочка «опубликовать анонимно» на пост. В контенте хранится снимок ника (`display_alias`), смена ника историю не переписывает. Смена — не чаще раза в `ALIAS_CHANGE_COOLDOWN_DAYS` (30 дней) |
| Аватарка | Галерея встроенная: 12 SVG лежат в репозитории (`app/static/img/avatars/`), загрузки файлов нет и не будет, поэтому нет ни хранения, ни модерации картинок, ни правок CSP. В БД хранится только ключ из белого списка `AVATAR_KEYS` (`app/core/avatars.py`), а `avatar_url` строит URL только из него — произвольная строка (в т.ч. `../`) в URL попасть не может |
| Актуальность аватарки | Картинка **всегда текущая**, а не снимок (в отличие от `display_alias`): подтягивается одним запросом на страницу через `students_repo.avatar_keys_by_id`, поэтому смена видна и под старыми записями |
| Аватарка и анонимность | Персональная картинка под анонимной записью не показывается никогда, и решает это `avatar_image_key` внутри макроса `avatar`, а не вызывающие — иначе одного забытого вызова хватило бы, чтобы анонимный пост деанонимизировал автора |
| Смена аватарки | Свободная, без кулдауна (в отличие от псевдонима). Учителя без аккаунтов остаются с кружком-инициалом; в админке картинка только в карточке ученика |
| Сессия ученика | Подписанная cookie без срока действия (`itsdangerous`), таблицы сессий нет: вход живёт, пока ученик не выйдет сам. Серверного отзыва нет; бан проверяется по БД на каждом запросе. Браузеры умеют урезать срок хранения cookie (~400 дней) — тогда потребуется повторный вход |
| Сессия админа | Серверные сессии в `admin_sessions`, в БД — только SHA-256 хэш токена, отзыв через logout |
| Пароли админа | argon2 (`argon2-cffi`), первый админ — скриптом `scripts/seed_admin.py` |
| Коды приглашения | Одноразовые, 12 символов (60 бит), в БД — HMAC-SHA256 от кода с ключом `SECRET_KEY`. Остаются **параллельным** способом входа и после порога саморегистрации; у таких учеников нет email/пароля |
| Rate limit | Счётчики в памяти процесса (один инстанс), скользящее окно по ученику. При росте нагрузки — таблица |
| CSRF | Подписанный double-submit: токен в cookie `csrf_token` и в скрытом поле формы. Таблицы токенов нет; проверяется каждый небезопасный метод, включая вход и выход |
| Отклонение при блоке ПДн | Жёсткий блок — отказ, контент не сохраняется. Мягкое срабатывание — текст сохраняется уже с плейсхолдером, в очередь идёт усечённый фрагмент |
| Журнал блокировок ПДн | Отказ по жёсткому правилу пишется в `pii_blocked_attempts`: кто, когда, что публиковал и какие правила сработали. Текста нет вовсе — ни строки, ни фрагмента |
| Что хранится в посте | **Оригинал** автора, в котором заменены только совпавшие фрагменты. Переносы строк и пробелы сохраняются. Нормализация (NFKC, невидимые символы, схлопывание пробелов) нужна только для проверки фильтром |
| Мат и грубые слова | **Разрешены** и в постах, и в псевдонимах: не блокируем и не заменяем. Никаких словарей — модерация только по жалобам |
| Лимит попыток входа | Скользящее окно по IP клиента, тот же ограничитель в памяти. `/admin/login` — жёстко (5 за 15 мин), `/login` — мягко (20 за 15 мин); отказ — `429` + `Retry-After`; успешный вход обнуляет счётчик. IP — только ключ счётчика в памяти, нигде не сохраняется и не логируется |
| Саморегистрация по email+паролю | Открыта, пока всего учеников (инвайтные тоже считаются) меньше `OPEN_REGISTRATION_LIMIT` (30). Порог — общий счётчик за всё время, проверяется в той же транзакции, что и вставка |
| Регистрация по QR | После 30-го — единственный самостоятельный способ входа, кроме инвайта. QR-токен живёт `QR_TOKEN_TTL_HOURS` (24ч), в БД только HMAC-хэш; подтверждает любой действующий ученик. Новый аккаунт получает пароль и сразу сессию |
| Хранение QR-токена у новичка | Серверных сессий нет, поэтому новичок носит свой токен в подписанной cookie `qr_registration` — только для перерисовки/обновления/поллинга страницы; доступа сам по себе он не даёт |
| Запрет индексации | `X-Robots-Tag: noindex, nofollow` на каждом ответе (middleware outermost) + `/robots.txt` с `Disallow: /`. `<meta name="robots">` в шаблонах **нет** — он дублирует заголовок и легко теряется на странице, не наследующей `base.html` |
| Флаги cookie | У всех cookie: `httponly`, `secure=COOKIE_SECURE`, `path=/`. Админская `admin_session` — `SameSite=Strict` (вся админка same-site, «снаружи внутрь» с сессией не ходит); ученическая, QR- и CSRF-cookie — `SameSite=Lax` (есть переходы между страницами сканера и QR-регистрации, выгода от Strict ниже). Проверки `COOKIE_SECURE` и `SECRET_KEY` — предупреждением в лог на старте, а не отказом старта |
| Лимиты длины ввода | Контентные лимиты живут константами в сервисах (`MAX_POST_LENGTH` и др.), капы полей аутентификации — в `app/config.py` (`MAX_EMAIL_LENGTH`, `MAX_PASSWORD_LENGTH`, `MAX_INVITE_CODE_INPUT_LENGTH`, `MAX_ADMIN_USERNAME_LENGTH`, `INVITE_TTL_MAX_DAYS`) и рендерятся как `maxlength`/`max` из Jinja-глобалов. Проверка длины идёт **до** регэкспов и хэширования; pydantic-схемы намеренно не ужесточены — иначе форма отвечала бы `422` вместо перерисовки с понятным текстом |
| Логи | Один логгер `app` (`app/core/logging.py`), события вида `event key=value` латиницей. Отказы — warning: `csrf_refused`, `login_throttled`, `publish_rate_limited`; события без отказа — info: `publish_pii_blocked`, `admin_login_failed`, `student_login_failed`. В логи **никогда** не попадают тексты постов и комментариев, псевдонимы, email, логины, IP, query-строка, коды приглашений и QR-токены — только метод, путь без query, тип объекта и коды сработавших правил |
| Расписание и ДЗ — данные, а не код | Уроки и задания заливаются `scripts/seed_demo.py`, в интерфейсе не редактируются: сетка «класс × день × номер урока» и «класс × предмет × дата сдачи». Класс ученика — колонка `students.class_name`, и это персональные данные: он виден только в своём профиле, рядом с постами класса нет. Время урока — текст `"08:30"`, а не `Time`: с ним сравнивает только шаблон |
| Ассистент | Гибрид: сначала ответ по базе школы (расписание, домашка, учителя, турниры), и только если база не знает — вопрос уходит модели. Ключ модели (`ANTHROPIC_API_KEY`/`OPENAI_API_KEY`/`DEEPSEEK_API_KEY`) по умолчанию пуст, и тогда **наружу не уходит ничего**. Уходит вопрос и обезличенный контекст (уроки на сегодня и ближайшая домашка класса): ни псевдонима, ни класса, ни почты, ни постов. Ключ и текст вопроса не логируются; ответ помечен источником, чтобы ответ модели не читался как выписка из школьной базы. Проверено, куда ходить и чем — тоже настройки: `*_MODEL` и `*_BASE_URL` (15.10.2026, см. «Стенд для жюри на Render») |
| Асинхронные действия | Лайк, публикация, комментарий, вопрос ассистенту, аватарка, псевдоним и заявка в команду уходят `fetch`'ем на JSON-двойника того же маршрута (`/api/...`) и меняют страницу на месте; `window.location.reload` в проекте нет. Тело — по-прежнему форма, а не JSON: так работает та же проверка CSRF (`require_csrf`), без второй её реализации. Ответ — разметка того же шаблона, что рисует страницу (`_post_card.html`, `_comment.html`), а не JSON-объект: карточка в ленте и карточка, вставленная скриптом, — один шаблон и не могут разойтись. Отказ ученик может исправить → `200` + `{"ok": false, "error": "..."}` рядом с формой; лимит частоты → `429`. У каждой формы остаётся настоящий `action` на настоящую страницу: без скрипта всё работает как форма, а не отдаёт JSON в браузер |
| Заявки в команду | Одна заявка на ученика (`dev_applications`, уникальный ключ по `student_id`): повторная отправка заменяет прежнюю, а не плодит строки. Ник хранится в одном виде (`@name`) и проверяется по форме, без походов в Telegram. Сайт никуда заявку не отправляет — её читает админ на `/admin/dev-applications` и отвечает в Telegram руками |
| Киберспорт | Турнир — запись о событии, награда — ребро «ученик × турнир × код награды» (`student_badges`) с уникальным ключом: один и тот же бейдж за один турнир не выдаётся дважды. Колонки-счётчика на ученике нет — он разошёлся бы с фактами. Коды игр и наград живут в базе, подписи — в `app/services/esports.py` |
| Дизайн | «Жидкое стекло»: панели — полупрозрачные листы с `backdrop-filter`, за ними цветные огни на `body::before`; кнопки — белое стекло на 10 % (`--control`), нажатие — `scale(.95)`. Палитра — эппловская тёмная (`#09090b`, акцент `#0a84ff` только на иконках и фокусе), цветных градиентов и «неоновых» кнопок нет: цвет означает состояние (красный — отказ, зелёный — успех), а не украшение. Ни Tailwind, ни сборки, ни CDN — поэтому классы вида `backdrop-blur-xl` переведены в собственные токены CSS. Всё оформление в трёх файлах, анимации — чистый CSS, отключаются `prefers-reduced-motion` |
| Отложено осознанно | Загрузка изображений (аватарка — **не загрузка**: это выбор из встроенной галереи, а загрузка изображений по-прежнему отложена), личные сообщения между учениками, 2FA для админа, хранение IP. (Email у учеников больше не отложен — введён саморегистрацией, см. ниже) |

Следствия для безопасности, о которых надо помнить:

- Контент виден только с валидной сессией; поисковая индексация запрещена целиком — заголовком
  `X-Robots-Tag: noindex, nofollow` на каждом ответе и файлом `/robots.txt` (этап 13).
- Забаненный ученик получает `403` и не читает и не пишет — проверка идёт по БД, а не по cookie.
- Ученик несовершеннолетний: реальные имена, адреса и контакты не должны попадать в публичный текст — этим занимается фильтр ПДн.
- Ничего личного не должно попадать в **query-строку**: собственные события логируют путь без
  query, но access-log uvicorn в проде печатает строку запроса целиком. Формы отправляют данные
  телом POST, query у нас не несёт ни email, ни псевдонимов, ни кодов — это инвариант, который
  нужно держать.
- `COOKIE_SECURE=false` в разработке; за HTTPS включается `true`. При старте приложение пишет
  предупреждение в лог, если `COOKIE_SECURE=false` вне `DEBUG` или если `SECRET_KEY` остался
  дефолтным, — но не отказывается стартовать (этап 13).

### Отклонения от исходного плана

- **Этап 1:** из `invites` удалена колонка `used_by` — она вместе с `students.invite_id`
  давала циклическую зависимость FK, на которой Alembic писал предупреждение. Кто погасил
  код, определяется запросом по `students.invite_id`.

## Школьные данные, ассистент и «жидкое стекло» (13.10.2026)

Этапы 16–20 сделаны одним заходом. Почему так, а не иначе:

- **Расписание, ДЗ и турниры — данные, а не код.** Ни одного названия предмета, игры или
  награды нет ни в шаблоне, ни в роутере: в базе лежат коды (`cs2`, `mvp`, `live`), подписи —
  в словарях `app/services/{school,esports}.py`, и тесты сверяют, что на каждый код есть
  подпись и наоборот. Незнакомый код не роняет страницу: он показывается как есть.
- **Класс ученика — персональные данные.** `students.class_name` решает, какое расписание
  видит ученик, но рядом с постами он не показывается никогда: фильтр ПДн считает номер
  класса мягким ПДн в публичном тексте, и профиль — единственное место, где класс виден.
  Ученик без класса получает честное «класс не указан», а не чужое расписание.
- **Сидер идемпотентен по естественным ключам**, а не по «уже залито»: урок — по
  `(класс, день, номер)`, задание — по `(класс, предмет)`, заметка — по `(класс, текст)`
  (заметок на день бывает несколько, ключ по дате затирал бы все, кроме последней), турнир —
  по `(игра, название)`, награда — по тройке из уникального индекса, ученик — по псевдониму,
  пост — по тексту. Домашка и заметки считаются от сегодняшнего дня, поэтому демонстрация не
  устаревает, а повторный запуск сдвигает срок, а не плодит вчерашние строки. Опечатка в
  данных (псевдоним, которого нет) останавливает заливку с ошибкой: половина демо-данных
  хуже, чем ничего.
- **Пароль демо-аккаунта в репозитории не лежит.** `--with-login` привязывает к одному
  ученику почту и случайный пароль и печатает их один раз; `--password` позволяет задать
  свой.
- **Ассистент ходит наружу только с ключом.** Ключ пуст по умолчанию, и тогда ни один запрос
  не покидает сервер — это проверено тестом, который подменяет вызов модели на «упасть»: без
  ключа он не должен быть вызван вовсе. Вопрос, на который отвечает база, до модели тоже не
  доходит: модель занимается только тем, чего в школьной базе нет. Обфускации текста нет
  никакой — уходит сам вопрос, поэтому в системной подсказке прямо запрещено просить и
  повторять личные данные, а контекст обезличен по построению (см. таблицу решений).
- **Модель вызывается через `httpx`, а не через SDK.** Официальный SDK есть только у одного
  из двух провайдеров, а требование — гибрид «Claude/DeepSeek» за одной функцией; SDK одного
  вендора ради этого тянуть не стали. Разбор ответа — единственное место, знающее формат
  провайдера, и он изолирован в `_ask_anthropic`/`_ask_deepseek`.
- **Дизайн переписан, логика — нет.** Переписаны `theme.css`, `layout.css`, `components.css`
  и шаблоны экранов; роутеры, сервисы и репозитории затронуты только там, где экрану нужны
  данные (погода дня на главной, награды в профиле). CSS-токены переименованы в термины
  стекла (`--glass`, `--glass-line`, `--glass-blur`), старые имена `--surface-glass*`
  оставлены псевдонимами: их всё ещё спрашивает `login.css`.
- **Правка тестов при редизайне — по существу, а не «чтобы прошло».** Два теста аватарок
  утверждали «на странице нет ни одной картинки из галереи». После редизайна верхняя панель
  рисует картинку *самого смотрящего*, и это утверждение стало ложным по замыслу. Теперь
  проверяется то, что защищалось: карточка анонимного поста не несёт картинки автора, а у
  учителя её нет нигде (единственная картинка на странице — своя, в панели). Свойство не
  ослаблено: тест по-прежнему падает, если картинка появится в карточке.

## Жесты, «жидкое стекло» и установка на домашний экран (13.10.2026)

Косметический проход по уже готовому интерфейсу и PWA-обвязка: стекло стало «жиже», меню
получило жесты и эффект увеличения, сайт — манифест и значки. Логики не тронуто: ни моделей,
ни сервисов, ни репозиториев; в роутерах появился один публичный маршрут за манифестом.

- **Свайп — это переход между страницами, и он это не скрывает.** Настоящей прокрутки двух
  страниц быть не может: соседняя ещё не загружена, за пальцем нечего тянуть. Поэтому движение
  собрано из двух половин — уходящая страница уезжает и тускнеет, приходящая выезжает с той
  стороны, откуда шёл палец. Направление передаётся флагом в `sessionStorage`, который
  снимается на первом же рендере: флаг, оставшийся лежать, анимировал бы чужую загрузку.
- **Соседи — это пункты нижнего меню, а не список в скрипте.** Скрипт читает `href`'ы таб-бара,
  так что порядок разделов задан в одном месте (`_bottomnav.html`), а не продублирован в JS.
  Страница раздела владеет и своими подстраницами (`/feed` — и `/feed/posts/7`), поэтому
  совпадение по префиксу. Страница, которой в меню нет (пост, учитель, сканер), соседей не
  имеет и жеста не получает — это не забытый случай, а защита от перехода «в никуда».
- **Жест уступает тому, что делает то же движение.** Горизонтальный свайп начинается только
  если палец пошёл явно вбок (иначе страница просто скроллится), и никогда не начинается в
  поле ввода или в горизонтально прокручиваемом блоке (`.table-scroll` в админке) — там
  движение принадлежит элементу.
- **Активный пункт меню — «капля света», а не покрашенная вкладка.** Подсветка переехала из
  пункта в отдельный элемент, который перетекает между вкладками; во время свайпа он
  показывает, куда палец приведёт, ещё до того, как палец отпущен. Без скрипта каждый пункт
  красится сам, как раньше: `.bottomnav.is-js` включает каплю, её отсутствие — старое
  поведение. Ничего не сломается, если `swipe.js` не загрузится.
- **`swipe.js` — четвёртый скрипт сайта, и CSP его уже разрешает.** `script-src 'self'`
  пускает файлы из `/static` и по-прежнему запрещает инлайновые: запрет стережёт
  `test_no_inline_scripts_in_templates`, который читает все шаблоны.
- **Доводка стекла — в токенах, а не в правилах.** Диагональный блик (`--glass-sheen`), двойной
  рант (`--glass-highlight`), двойная тень (контактная + рассеянная) и более круглые радиусы
  заданы один раз в `theme.css`; `layout.css` и `components.css` их только спрашивают. Новое
  движение (пружина `--transition-spring`, переход страниц, нажатие на пункт меню) выключено
  в `prefers-reduced-motion` — как и всё остальное движение в проекте.
- **Увеличение значка — это позиция пальца, а не анимация.** Скрипт на каждое движение
  пересчитывает две переменные (`--dock-scale`, `--dock-lift`) для каждого значка по
  расстоянию от пальца, CSS только показывает, как изменение этих переменных выглядит.
  Отсюда квадрат в формуле: под пальцем рост почти не тормозится, а ко второй вкладке уже
  затухает — как у лупы. Затухание считается в ширинах вкладки, а не в пикселях, поэтому на
  узком экране эффект тот же формы, а не резче. Пружина включается только на отпускании:
  под пальцем значения меняются каждый кадр, и переход лишь отставал бы от них.
- **Манифест лежит в корне репозитория, а отдаётся роутом.** Браузер ищет манифест в корне
  сайта, а из `/static` корнем был бы `/static` — поэтому файл рядом с кодом (как `/robots.txt`:
  ничего из корня репозитория иначе не отдаётся) и публичный роут `GET /manifest.json`.
  Публичный намеренно: установка происходит до входа, а за логином манифеста не прочитает
  никто. Данных в нём нет — только оболочка.
- **`start_url: "/"` — потому что вход теперь один на всех.** Вошедшего `/` отправляет в ленту,
  остальных — на форму входа; отдельного «стартового адреса приложения» не завелось, и это
  хорошо: иначе он разошёлся бы с настоящим входом на сайт.
- **Менять сессию не пришлось: она уже постоянная.** Кука входа выдаётся с `max_age`
  (`_set_session_cookie`) и на весь сайт (`path="/"`), вход свой — наружу за токеном сайт не
  ходит, а кнопки OAuth — заглушки. Поэтому в оболочке нет ни одного шага, за которым
  пришлось бы выпрыгнуть в Safari: единственное, что нужно знать — iOS держит у установленного
  приложения своё хранилище, и войти в нём надо один раз (сессия Safari внутрь не переносится).
  Дальше кука живёт до срока, потому что она не сессионная. Отсутствие выхода наружу проверяет
  тест, который ищет `target="_blank"` по всем шаблонам разом.
- **`viewport-fit=cover` — не украшение.** Без него `env(safe-area-inset-*)` в Safari равны
  нулю, и `black-translucent` (фон под прозрачной строкой состояния) оставил бы шапку, экран
  входа и первую панель под часами. Отступы добавлены второй декларацией, а не `calc` внутри
  шортката: браузер, не знающий `env()`, сохранит прежний отступ, а не останется без него.
- **Значки рисует скрипт, а лежат они готовыми.** `scripts/make_icons.py` — тот же подход, что
  у шрифтов: в репозитории бинарник, сборки нет, а происхождение записано. Рисуется вчетверо
  больше и уменьшается (у Pillow нет сглаживания растра), градиент и затухание света считаются
  вручную: у `Image.radial_gradient` «радиус» задан манхэттенским расстоянием, и круг выходил
  ромбом с ровными диагональными границами прямо на значке.

## Асинхронные формы, модель у ассистента и заявки в команду (13.10.2026)

Проход по интерфейсу и поведению: палитра стала эппловской тёмной, каждое действие на
сайте перестало перезагружать страницу, ассистент научился спрашивать модель, профиль
получил заявку в команду разработки. Ничего из уже принятых решений не отменено: ПДн
фильтр, лимиты, постмодерация и права остались те же.

- **Tailwind не появился, хотя задача была написана его классами.** Проект — чистый CSS
  без сборки, без CDN и с CSP, запрещающим инлайновые стили и скрипты; подключить
  Tailwind значило бы завести сборку и наружу-зависимость. Поэтому каждый затребованный
  класс переведён в существующие токены: `bg-white/[0.04]` → `--glass`,
  `backdrop-blur-2xl` → `--glass-blur-strong`, `active:scale-95` → `button:active
  { transform: scale(.95) }`, `rounded-full` → `--radius-pill`. Это отклонение от буквы
  задачи и сознательное: палитра и поведение те же, инструмент — тот, что в проекте.
- **Нижнее меню больше не накрывает контент.** Отступ снизу — токен `--dock-clearance`
  (высота меню + 4.5rem) на `body` и на псевдоэлементе-затухании; мобильная ширина
  показывает меню, широкая — верхнее. Шапка не переносится, а тонеет: подписи пунктов
  убираются в невидимый-но-доступный текст (не `display: none` — у ссылки остаётся имя для
  скринридера) на двух порогах, 1180px и 980px.
- **Стекло для карточек и стекло для панелей — одна материя, но разной плотности.**
  Шапка и док сделаны теми же 6 % белого с размытием (`--dock`, `--dock-line`,
  `--dock-blur`), что и остальное стекло: разная материя у верхней и нижней кромки одного
  экрана выглядит как два приложения, поставленные друг на друга. Исключение одно —
  прокрученная шапка: 4 % белого поверх едущего текста не читаются, там нужна толщина
  (`--bar-strong`).
- **`require_csrf` переиспользован, а не переписан.** JSON-эндпоинты под `/api` принимают
  тело формы (`Form(...)`) именно поэтому: разбор токена из тела уже есть, и второй
  проверки в проекте не появилось. Докстринг зависимости поправлен — раньше он запрещал
  такое переиспользование.
- **Лайк переключается оптимистично, но правда одна — серверная.** Сердце и счётчик
  меняются на нажатии, ответ сервера их переписывает; отказ возвращает прежние значения.
  У каждой формы свой номер запроса, поэтому два быстрых нажатия не оставляют счётчик в
  состоянии более медленного ответа. Состояние всё равно считается по сессии, а не берётся
  из тела.
- **Отказ — контент, а не ошибка.** Переписывать страницу целиком ради «слишком длинно»
  незачем, а `4xx` заставил бы браузер считать обычный отказ ошибкой, поэтому отказ ученику
  приходит `200` и текстом (тем же, что у формы — формулировки переехали в сервисы:
  `feed.refusal_message`, `aliases.refusal_message`, `team.refusal_message`, чтобы у двух
  входов не разошлись слова). `429` остался за лимитом частоты.
- **Окно заявки — `<dialog>` плюс настоящая страница.** `showModal()` даёт верхний слой,
  Escape и недоступность остальной страницы для Tab — ничего этого позиционированный `<div>`
  не получает без скрипта, воюющего с браузером. Но `<dialog>` без скрипта не откроется, а
  кнопка, которая молча ничего не делает, — хуже, чем её отсутствие: поэтому кнопка —
  ссылка на `/me/dev-apply` с той же формой, а скрипт лишь перехватывает открытие.
- **Заявка сохраняется, а не отправляется «в никуда».** Форма, ответы на которую никто не
  может прочитать, врёт заполнившему: появилась таблица `dev_applications` (миграция
  `0009`), строка на ученика, админский экран и счётчик на панели. Ответ на заявку — по
  Telegram руками, автоматических сообщений сайт не шлёт.
- **Разметку ассистента строит сервер, и экранирует перед тегами.** `app/core/markdown.py`
  сначала экранирует весь текст ответа и только потом добавляет свои теги из закрытого
  списка (`p`, `br`, `h3`, `ul`, `ol`, `li`, `strong`, `code`, `pre`): ссылок, картинок и
  HTML-насквозь в нём нет. Библиотеку Markdown подключать значило бы пустить чужой HTML в
  страницу; рендерить в браузере — держать вторую (JS) реализацию экранирования рядом с
  первой. Тест проверяет в том числе, что `<script>` и `<img onerror=...>` из ответа модели
  приходят текстом.
- **Кнопка «Загрузить фото» — демонстрация, и говорит об этом.** Загрузки файлов на сайте
  нет и не будет (решение про аватарку не менялось), поэтому кнопка отвечает всплывающим
  сообщением, а не открывает пустой выбор файла. Молчащая кнопка заставляет искать поломку
  у себя.
- **Провайдер модели выбирается по заполненному ключу.** У OpenAI и DeepSeek общий клиент
  (`/chat/completions`), у Anthropic — свой формат; если заполнено несколько ключей,
  побеждает первый по порядку в `.env.example`. Идентификатор модели — настройка
  (`OPENAI_MODEL` и т. п.), а не константа: у OpenAI идентификаторы приходят и уходят, и
  значение по умолчанию здесь отправная точка, а не обещание.

## Док, шапка и свайп по капсуле (13.10.2026)

Доводка панелей навигации: док стал плавающей капсулой, шапка — той же материей, у
капсулы появилось собственное поведение при свайпе.

- **`!important` из задачи не появился, и теперь это проверяет тест.** Все правила
  приходят от токенов, а не от громкости селектора; `tests/test_shell.py` обходит все
  файлы `app/static/css` и падает на любом `!important`.
- **Из трёх значений фона выбрано одно.** В задаче их было три подряд
  (`rgba(30,30,35,.65)`, `rgba(255,255,255,.08)`, `rgba(255,255,255,.06)`) — это три
  разных материала для одной панели. Док и шапка взяли последнее (`--dock`), потому что
  цветной тёмный тон в палитре, построенной на белом поверх обсидиана, читается как
  чужая вставка; размытие — 24px, а не 35px: это радиус, который Safari держит на GPU,
  длиннее — и фиксированная панель на iOS становится непрозрачной.
- **Отступ снизу считается от реального следа дока, а не от высоты бара.** Буквальное
  «высота меню + safe-area» (~72px) меньше, чем капсула занимает с зазором и скруглением;
  сохранён `--dock-clearance` (140px) плюс `env(safe-area-inset-bottom)`, а сам инсет
  сверху несёт липкая шапка, а не контейнер: иначе на iOS он отсчитался бы дважды.
- **Капля едет за пальцем и поднимается — но не через `transform`.** Скрипт переписывает
  `transform` каждый кадр, поэтому подъём сделан отдельным свойством `scale` (у него своя
  `transition` и своя пружина), а класс `is-swiping` живёт ровно столько, сколько длится
  жест. Тест проверяет обе половины: что `transform` в правиле подъёма нет и что класс
  снимается в обеих ветках — и на отпускании, и на отмене.
- **Ход капли зажат внутрь бара.** Позиция считается от прямоугольника вкладки, а тот мог
  быть измерен в момент переразметки (поворот, опоздавший веб-шрифт), и последняя вкладка
  оказывалась на волос шире оставшегося места. Капля имеет право не дойти до края, но не
  право вылезти за него.
- **Док и шапка называют один раздел одинаково.** «Игры» в доке стали «Турнирами», как в
  шапке и на странице. Второе расхождение — «Уроки» в доке против «Расписания» в шапке —
  оставлено сознательно: «Расписание» в доке из пяти вкладок переносится на вторую строку
  на узких телефонах, а перенос строки в доке ломает всю капсулу.
- **Выход из аккаунта в бургер-меню намеренно не попал.** Меню на телефоне открывается
  промахом; вылететь из аккаунта от промаха ученик не должен. Выход живёт только в
  профиле.
- **Рефракция (`feDisplacementMap`) не подключена.** Это трюк одного WebKit: везде
  остальной он невидим, а стоит полной перерисовки страницы на каждом кадре прокрутки.

## Мобильный редизайн: три прохода (13.10.2026)

Задача: довести интерфейс до вида iPhone-приложения в Safari на ширине ~390px. Сделано
тремя проходами, каждый — отдельным коммитом с зелёными тестами; проход 1 — док.

### Проход 1. Док как капсула с линзой

- **Из трёх фонов задачи снова выбран один.** `rgba(255,255,255,.07)` — то же стекло, что
  у шапки, только на процент плотнее; цветного `rgba(30,30,35,…)` в палитре нет намеренно.
  Размытие 22px, а не 35px: 24px — предел, который Safari держит на GPU, всё длиннее
  уезжает с композитора и панель становится непрозрачной сама.
- **У бара фиксированная высота, а не по содержимому.** Линза выше вкладки (56px против
  52px внутри отступов), и бар, подстраивающийся под самое высокое в себе, рос бы и опадал
  на каждой вкладке, по которой проходит линза. Отсюда `height: var(--nav-h)` = 68px и
  `--dock-lens-h` = 56px.
- **Линза измеряется по прямоугольнику вкладки.** Деление ширины бара на пять вкладок
  разошлось бы на пиксель за вкладку из-за зазоров; `getBoundingClientRect` вкладки —
  единственный источник правды, он же пересчитывается на `resize`, `orientationchange`,
  `load` и `document.fonts.ready` (для этого у `--dock-lens-h` есть токен: высоту скрипт не
  мерит вовсе).
- **Линза шире вкладки, поэтому её ход зажат.** 12px сверх ширины вкладки, и на первой и
  последней вкладке линза свисала бы с закруглённого конца капсулы; зажим по внутренней
  ширине бара и 8px внутреннего отступа оставляют ей запас даже на `scale: 1.15` под
  пальцем.
- **Перетаскивание по бару — это не свайп по странице, но линза у них одна.** Там палец
  тянет страницу и линза показывает, куда приедешь; здесь палец тянет линзу. Оба жеста
  заканчиваются загрузкой страницы и оба зовут `moveBlob`, поэтому вторая реализация линзы
  не появилась.
- **Щелчок после перетаскивания гасится — ровно один.** Палец, проехавший по бару, метил в
  другую вкладку, а браузер после `pointerup` шлёт `click` по той, где палец начал: без
  подавления перетаскивание открывало бы не то, что показывала линза. Слушатель стоит на
  баре в фазе перехвата; обычное нажатие (сдвиг меньше 6px) не подавляется вообще — ссылка
  работает как ссылка.
- **Инерция — на конце жеста, а не под пальцем.** Пока палец ведёт, линза идёт за ним один
  к одному: отстающая линза делает следующую вкладку угадываемой. Вес появляется на
  отпускании — перелёт `--transition-dock` (350ms, `cubic-bezier(.34,1.56,.64,1)`) и флик:
  если палец выпустили на скорости больше 0.55px/мс, линза уходит на вкладку дальше.
  `prefers-reduced-motion` отключает и перетаскивание, и лупу — нажатия остаются.
- **Радужная кайма — только там, где её можно вычесть из фона.** Кольцо 1px из
  `conic-gradient` под `mask-composite: exclude`; без поддержки вычитания маски оно залило
  бы линзу целиком, поэтому вся кайма заперта в `@supports`, а в остальных случаях остаётся
  обычная волосяная рамка. Цвета — 20–30 % альфы: полный оборот оттенков вокруг пилюли в
  78px превратил бы навигацию в светящуюся вывеску.
- **Притушенные вкладки — на ссылке, а не на её содержимом.** `opacity: .6` на `.bottomnav > a`
  и `1` на `.is-active`: невидимая вкладка гаснет целиком, иконка и подпись вместе. Линза —
  это `span`, поэтому правило притушевания на неё не попадает.
- **Без `backdrop-filter` капсула непрозрачная.** `@supports not` отдаёт ей `--surface-1`:
  полупрозрачность без размытия — единственный случай, когда текст страницы читается сквозь
  подписи, а полоса навигации этого позволить себе не может.

### Проход 2. Комментарии, формы и лайки комментариев

- **Лайки комментариев сделаны — решение «лайков у комментариев нет» отменено** (записано
  было в разделе про лайки выше, там же и оговорено). Отдельная таблица
  `comment_likes (student_id, comment_id)` с индексом `uq_comment_likes_student_comment`
  (миграция `0010`), а не пара необязательных полей в `post_likes`: с двумя настоящими
  внешними ключами база сама отказывает отметке на несуществующий комментарий, чего пара
  nullable-колонок не умеет. Тумблер — второй функции (`toggle_comment_like`), а не один
  общий помощник: у них разные модели и разные таблицы, и общий помощник первым делом
  выяснял бы, что ему передали.
- **Комментарий ищется вместе с постом из адреса.** `_get_visible_comment` требует, чтобы
  `comment.post_id` совпадал с постом в URL, иначе `404`: иначе лайк, отправленный на один
  пост с идентификатором комментария из другого, прошёл бы, а страница показала бы
  закрашенное сердце не там, где оно стоит.
- **Формы поста и комментария — одна строка.** Поле на одну строку, которое скрипт растит до
  четырёх (`data-autogrow`), измеряя `scrollHeight` от `auto`, иначе поле, из которого
  стёрли текст, не опускается обратно. Высота считается в строках, а не в пикселях: строка и
  отступы читаются из `getComputedStyle`, поэтому скрипт и CSS не расходятся при смене
  типографики.
- **Кнопку отправки выключает только скрипт.** В разметке это обычная кнопка: браузер без
  скрипта обязан уметь отправить форму, поэтому `disabled` ставится из JS (и возвращается
  после `form.reset()` в конце обработчика — единственное место, где это видно всем формам
  сразу).
- **«Анонимно» — чип, а не галочка с подписью.** Плашка нарисована на `<span>` внутри
  `<label>`, поэтому выбранное состояние — `input:checked + span`, без `:has()` и без
  скрипта. Сам чекбокс остаётся в порядке табуляции и просто уведён из виду; обычная форма
  этого контрола (`.checkbox`) осталась на страницах настроек.
- **Комментарий — поток, а не список карточек.** Аватарка в своей колонке (32px), под ней
  волосяная линия до следующего комментария (`::after` с `flex: 1` — высота берётся из
  строки, а не задаётся числом; у последнего комментария линии нет), рядом одной строкой имя
  и время, под ними текст и два маленьких действия.
- **Жалоба спрятана за «...».** Это `<details>`, который открывается без скрипта, а ссылка
  внутри — обычная ссылка на страницу `/report/...`; скрипт только закрывает открытое меню
  по тапу мимо и по Escape — тем же слушателем, что закрывает меню в шапке. Панель меню
  берёт `--bar-strong`: под ней текст карточки, а не свет страницы, и меню должно читаться
  поверх того, что закрывает.
- **Толчок сердца — 1 → 1.3 → 1 за 200ms** (`heart-pop`), вместо прежней заливки с
  масштабом от 0.6: анимация теперь одинакова для перезагрузки (Post/Redirect/Get) и для
  скрипта, который закрашивает сердце на месте.
- **Макросы вместо копий разметки.** `like_button`, `report_menu` и `comment_actions`
  держат одинаковый почерк формы лайка (CSRF, `next_url`, JSON-двойник в `data-api`) у поста
  и у комментария: `_comment.html` — тот же файл, что рисует страница, и то, что вставляет
  скрипт, поэтому разойтись они не могут. `_comment.html` строит адрес из
  `comment.post_id`, а не из `post` в контексте: частичный шаблон рендерится и отдельно, с
  одним комментарием на руках.
- Тесты — `tests/test_likes.py` (лайки комментариев: тумблер, ограничение в схеме, счётчики
  и сердца на странице поста, чужой/скрытый/несуществующий комментарий, CSRF, аноним),
  `tests/test_api.py` (JSON-двойник), `tests/test_async_ui.py` (у сердца под комментарием
  тот же контракт: `data-api` под `/api` и настоящий `action`).

### Круглая кнопка ассистента (13.10.2026, между проходами 2 и 3)

- **Это ярлык, а не второе место.** Кнопка ведёт по тому же адресу `/assistant`, что и
  вкладка дока, и живёт только внутри `{% if student %}` из `base.html`: на входе и в
  админке ассистента спрашивать некому, и кнопки там нет.
- **На самой странице ассистента её нет.** Открывать то, где уже стоишь, нечего, а над
  полем вопроса кнопка закрывала бы ровно то, к чему зовёт. Путь сравнивается с
  `request.url.path` — как в `_bottomnav.html`; отдельного флага в контексте не завели.
- **Низ — из доковой прокладки.** `bottom: calc(var(--dock-clearance) +
  env(safe-area-inset-bottom))`: кнопка висит в пустоте над капсулой и не спорит с линзой.
  Тот же токен держит и прокладку страницы, и растворяющийся край, — теперь их трое, и
  тест считает три использования, а не два.
- **Страница уступает кнопке её высоту — иначе та ложится на последнюю строку.** На
  `--dock-clearance` стоит *низ* кнопки, а её верх на 48px выше, то есть уже на территории
  контента: в ленте это ссылка «Раньше →», а на странице поста — круглая кнопка отправки у
  формы комментария, ровно в правом углу под кнопкой. Поэтому `body.has-dock` получает
  `--dock-clearance + --fab-h + --space-3`: высота кнопки берётся тем же токеном, что и её
  собственный размер, чтобы числа не разошлись. Прокладка висит на классе, а не на `body`:
  на экране входа ни дока, ни кнопки нет, а карточка там стоит по центру, и лишние 60px
  под ней просто сдвинули бы её вверх. `:has()` для этого не нужен — класс ставит
  `base.html` по той же проверке `{% if student %}`, что включает и док, и кнопку.
- **Материя — доковая.** `--dock-lens` и `--dock-line` с размытием `--dock-blur` плюс
  `--dock-shadow`: кнопка стоит вплотную к капсуле, и второй материал на таком расстоянии
  читался бы как чужой элемент. Без `backdrop-filter` — та же непрозрачная `--surface-1`,
  что у капсулы.
- **На широком экране кнопка скрыта вместе с доком** (`@media (min-width: 768px)`), потому
  что она принадлежит телу навигации, а тело навигации на десктопе — шапка: там колонка
  текста шириной 72rem, и плавающая кнопка у её края встала бы поверх строк.
- **Это `<a>`, а не `<button>`:** раздел живёт по адресу, и ссылка работает без скрипта.
  Иконка декоративная, имя несёт `aria-label="Ассистент"`.
- Тесты — `tests/test_shell.py` (кнопка есть на `/feed`, `/me`, `/esports`, `/schedule` и
  ведёт на `/assistant`, её нет на `/assistant`; класс `has-dock` есть на всех страницах с
  доком и его нет на входе; в CSS — фиксированное положение, круг `--fab-h` = 48px,
  доковая материя, прокладка страницы из трёх чисел, скрытие тем же правилом, что скрывает
  док, и непрозрачный запасной фон).

### Проход 3. Строки, типографика телефона и прижатый композер (13.10.2026)

- **У телефона своя шкала типа, а не тот же `clamp`.** На ширинах до 767px ступени
  переписаны числами в `:root`: тело — 17px (то, что iOS называет body text), заголовок
  экрана — 34px (ровно iOS Large Title), подпись — 13px. На 360px заголовок отдаёт два
  пикселя (30px) — там же, где ему перестаёт хватать места рядом с чипом. Шкала объявлена
  на `:root`, а не на `body`: размер спрашивают все — заголовок, поле, чип, кнопка, — и
  выросшее в одиночку тело оставило бы мелкий шрифт за собой прежним.
- **Отступы:** колонка страницы на телефоне начинается в 16px под шапкой (было 32px —
  это прочерк, который ничего не отделяет), низ — один токен, остальное несёт
  `body.has-dock`. На 380px вбок отдаётся ещё 4px (gutter 12px): 336px содержимого вместо
  328 — это и есть разница между шапкой в одну строку и в две. Панель на телефоне —
  16px внутреннего поля, как карточка в iOS; рамка панели двигается, содержимое — нет.
- **Шапка:** единственная её кнопка на телефоне — бургер — стала 44px (`--row-h`), знак
  рядом вырос до 36px, строка получила `min-height: 44px`: тридцать девятипиксельная
  кнопка в углу — та, по которой промахиваются.
- **Профиль — список, а не стопка карточек.** Экран собран из того, из чего собран
  «Настройки» в iOS: подпись группы над панелью (`.list-head`, капс с разрядкой, снутри не
  заголовок, а именно подпись над группой) и строки одинаковой высоты (`.list-row`,
  `min-height: var(--row-h)` = 44px) с шевроном на конце. Панель группы — то же `.glass`,
  у которого снято поле (`.list { padding: 0; overflow: hidden }`): строки доходят до
  скруглённого угла, а волосяная линия стоит **на стыке** (`+ .list-row`), а не рамкой у
  каждой строки, — одна линия на шов вместо двух. Шеврон — единственная иконка с `cls`:
  без своего класса он неотличим от ведущей иконки строки (в `ui.icon` добавился третий
  параметр `cls`, иконка `chevron` 18px). Строки-разделы несут акцентную иконку (они двери,
  как раньше плитки сетки), служебные — монохромные. Выход — такая же строка, только
  красная, и единственная: единственное на экране, что нельзя отменить.
- **Радиусы не менялись — и это решение, а не пропуск.** 26px панели, пилюли дока и
  скругление линзы читаются «каплей стекла» именно своей щедростью; на телефоне ни одно
  из этих чисел не измеряется неправильно. Работа с радиусом в проходе ровно одна: у
  группы строк `overflow: hidden`, иначе линия стыка вылезала бы за скруглённый угол.
- **Один композер на весь сайт.** Ассистент получил тот же `composer__form`, что лента:
  поле на одну строку, растущее до четырёх (`data-autogrow`), и круглая кнопка отправки;
  строка `.composer-foot` («кнопка под полем») удалена вместе с разметкой. Побочная
  выгода — контракт `syncComposer`: кнопка гаснет на пустом поле, а поле возвращается к
  одной строке после ответа, потому что это делает общий `send()`, а не отдельный код
  ассистента. Круглые иконочные кнопки заодно подросли с 40 до 44px (`.btn--icon`).
- **Поле вопроса прижато к доку.** На телефоне композер — `position: sticky` на
  `bottom: calc(var(--dock-clearance) + env(safe-area-inset-bottom))`, отдельной панелью
  (`.chat-composer`), а не внутри панели разговора: прижатый элемент обязан быть
  достаточно плотным, чтобы ответы уходили **под** него. Подсказки-чипы переехали над
  полем — всё, что оказалось бы ниже прижатого, уезжало бы под него. На широком экране
  прижатия нет: там колонка целиком в виду.
- **Микроанимации:** строки появляются лестницей (40ms шаг, дальше 200ms на всех) — как
  посты; нажатие подсвечивает строку и уводит шеврон на 2px — строка отвечает раньше
  страницы. `prefers-reduced-motion` снимает и то, и другое.
- **Мёртвое убрано:** `.link-grid`, `.team-card`, `.settings-card`, `.badge-list`,
  `.badge-card`, `.composer-foot` (последнее использование каждого ушло вместе с
  разметкой). Награды стали строками списка, а игра переехала **второй строкой** под
  названием турнира (`.list-row-sub`), а не значением справа: «Counter-Strike 2» на 360px
  не оставил бы названию места на одной строке с ним.
- Тесты — `tests/test_shell.py` (+5: шкала телефона и 360px, 44px строки и круглых кнопок,
  профиль-список с восемью шевронами и красным выходом, композер ассистента с прижатием,
  16px панели с оговоркой про `.list`). 583 теста зелёные.

## Важные посты, сброс демо и новая демонстрация (14.10.2026)

Задача пришла не как этап плана, а как просьба: «убери демо-данные и настрой заново,
добавь вип-пост про идею ученика, на которую ответили завучи, и данные про классы и
расписание, чтобы сайт был живым». Оказалось, что первая половина — это не данные, а
фича: у поста не было ни закрепа, ни пометки.

- **Закреп — колонка, а не таблица.** `posts.is_featured` (миграция 0011): закреп у поста
  ровно один, живёт и умирает вместе с ним, отдельного поля у связи не будет. Отдельная
  таблица `post_pins` завела бы вторую дату создания (когда закрепили), порядок закрепов
  и вопрос «что делать, когда пост удалили», — а спрашивают с неё было бы то же самое
  булево.
- **Закреплённые — только первая страница ленты.** `list_feed_page` собирает первую
  страницу как «закрепы (по времени, новее выше) + добор потока», а начиная со второй
  отдаёт обычную выборку со сдвигом `offset − число закрепов`. Так закреп не встречается
  дважды, когда поток дойдёт до его возраста. `count_visible_posts` закреп считает, как и
  раньше, поэтому «двадцать постов на страницу» и число страниц не меняются: закреп
  вытесняет один пост потока, а не добавляется к нему.
- **Закреп ставит только сидер.** У `create_post` флага нет: путь публикации ученика не
  должен уметь закреплять, а `set_featured` вызывается отдельно (и повторно при повторном
  запуске — демо-данные это состояние, а не разовое действие). Ручного переключателя в
  админке нет; захочешь — отдельной задачей, новый маршрут тянет за собой сверку таблицы
  маршрутов, CSRF и след модерации.
- **Ответ завучей — аккаунт, а не флаг.** Псевдоним «Администрация школы» — обычная строка
  ученика без класса; своей «официальности» в схеме нет, видно её только по подписи, и
  этого для демонстрации хватило. Настоящие ФИО в демо по-прежнему не попадают.
- **`--reset`.** Сброс вынесен в функцию с явным списком таблиц (`RESET_TABLES` /
  `KEEP_TABLES`): забытая таблица должна быть видна в коде, а не выясняться при заливке.
  Остаются `admins`, `admin_sessions`, `alembic_version` — иначе в панель не войти. Порядок
  шагов при пересборке важен: учителей сброс тоже сносит, а отзывы об них пишет
  `seed_demo.py`, поэтому `seed_teachers.py` идёт после `--reset`.
- **Демонстрация выросла:** 6 классов (8А, 8Б, 9А, 9Б, 10А, 10Б), 41 ученик (40 + аккаунт
  администрации), 187 уроков сетки, 32 задания, 5 турниров, 27 постов, 22 комментария,
  79 лайков, 5 отзывов. Идею ученика поддержали 36 лайков, и она открывает ленту — порядок
  закреплённых задаётся **местом в данных `POSTS`** (новее выше, как во всём потоке), а не
  отдельным порядковым полем; это зафиксировано тестом, иначе демонстрация зависела бы от
  того, какой кортеж написан первым.
- **Демо закрывает почтовую регистрацию — так и задумано.** `OPEN_REGISTRATION_LIMIT = 30`,
  в демо 41 ученик, `/register` уводит на QR. Поднимать лимит — только в локальном `.env`:
  в коде он держит тесты быстрыми.
- **Дрейф `dev_applications` из этой работы (не связан с демо):** `alembic check` ругается
  на миграцию 0009 — она объявила `UniqueConstraint('student_id',
  name='uq_dev_applications_student')` плюс неуникальный индекс, а модель просит
  `unique=True, index=True`. Дрейф воспроизводится на базе, собранной с нуля миграциями,
  то есть он был и раньше, а не появился с 0011. **Закрыт 15.10.2026 миграцией 0012** —
  см. «Дрейф `dev_applications` закрыт».

## «Мой класс» и выбор класса в настройках (14.10.2026)

Просьба была короткой — «добавь меню класса для реальных пользователей», — но упиралась в
дырку в продукте: класс ученику мог поставить **только сидер демо-данных**
(`students_repo.upsert_student`). Ни регистрация, ни настройки, ни админка `class_name` не
писали, поэтому у настоящего ученика класс был пуст, а `/schedule` честно советовал
«обратитесь к администрации школы», хотя идти было некуда. Поэтому работа состоит из двух
половин: раздел «Мой класс» и возможность выбрать класс.

- **Класс — расписание, а не справочник.** Список классов для выбора собирается
  `SELECT DISTINCT class_name FROM schedule_entries`: класс существует ровно там, где стоит
  его сетка. Отдельная таблица классов завела бы второй источник правды о школе и вопрос
  «кто заводит класс» — а спрашивают с неё было бы то же множество строк.
- **Выбор из списка, а не свободный ввод.** Класс — ключ, по которому ищутся расписание,
  домашка и одноклассники. Вписанное руками «9б» вместо «9Б» дало бы пустой экран без
  единого слова о причине; `<select>` такой опечатки не допускает. Свой текущий класс
  добавляется к списку, даже если сетки по нему уже нет (`available_classes(current=…)`):
  иначе поле показывало бы «не указан» там, где класс есть.
- **Порядок классов — школьный, а не строковый.** `_school_order` сортирует по
  `(номер, буква)`: обычная сортировка строк поставила бы «10А» перед «8А».
- **Класс — только из сессии.** Параметра с классом нет ни в адресе, ни в теле (кроме самой
  формы выбора): иначе чужую сетку уроков и чужой список псевдонимов можно было бы выпросить
  прямой ссылкой. Тест `GET /me/class?class=10А` это фиксирует. Кулдауна на смену класса нет,
  в отличие от псевдонима: класс — не имя, за которое можно выдать себя.
- **Забаненные в росписи не показываются.** Список класса — такая же витрина, как лента;
  вернуть в неё ученика, которого модерация убрала со всего сайта, значило бы отменить её
  решение. Запрос отдаёт три колонки (`id`, `alias`, `avatar_key`) — хэшу пароля в памяти
  страницы делать нечего.
- **Сортировка росписи — в Python, а не в SQL.** SQLite складывает кириллицу по коду
  символа: заглавные идут отдельной страницей перед строчными («Ёж» раньше «Абрикос»:
  Ё — U+0401, А — U+0410), а `NOCASE` в SQLite сворачивает только ASCII. `casefold` плюс
  замена «ё» → «е» (в Unicode «ё» стоит за «я») дают обычный русский алфавит.
- **Раздел живёт под `/me/`, а не на верхнем уровне.** В плане он назывался `/class`, но
  каждый существующий адрес верхнего уровня (`/feed`, `/schedule`, `/assistant`, `/esports`,
  `/scan`) стоит в доке и в шапке, а раздел, который открывают из профиля, живёт как
  `/me/settings` и `/me/dev-apply`. Отклонение от плана — сознательное.
- **Пункта в доке нет.** `tests/test_shell.py` ждёт в доке ровно пять ссылок, и это не
  формальность: док — ежедневный маршрут, а класс открывают не каждый день. Тест обновлён на
  одну строку профиля (8 строк-ссылок, 9 шевронов, 5 подписей групп).
- **Панели «Сегодня» и «Домашнее задание» — партиалы.** `_school_today.html` и
  `_homework_list.html` включены и в `/schedule`, и в `/me/class`: день недели, вид пустого
  дня и подсветка «сдавать сегодня» (её отдаёт `day_summary` ключом `date`) разошлись бы
  между страницами при первой же правке.
- **Пустой список классов — не ошибка ученика.** Если расписания в школе ещё нет, формы на
  `/me/settings` нет вовсе, а стоит подсказка: `<select>` с одним «Не указан» показывал бы
  выбор, которого нет.
- **`select` добавлен в стили полей.** Он был единственным неоформленным нативным
  контролом: на тёмной странице это светлый прямоугольник. `color-scheme: dark` в
  `theme.css` уже отдаёт системному списку тёмную тему.

## Дрейф `dev_applications` закрыт (15.10.2026)

`alembic check` на базе, собранной миграциями с нуля, ругался на `dev_applications`: миграция
0009 записала правило «одна заявка на ученика» дважды — `UniqueConstraint('student_id')` плюс
**неуникальный** индекс на тот же столбец, — а модель просит `unique=True, index=True`, то есть
один уникальный индекс. На уже работающей базе этого не видно: там просто лежат обе сущности.

- **Миграция 0012** снимает констрейнт и переставляет индекс уникальным: `drop_index` →
  `batch_alter_table` с `drop_constraint('uq_dev_applications_student')` → `create_index(unique=True)`.
  Индексы нарочно вне `batch_alter_table`: SQLite умеет `DROP INDEX` и `CREATE INDEX` напрямую, а
  пересобирать таблицу приходится только из-за констрейнта (`DROP CONSTRAINT` в SQLite иначе
  невозможен). Констрейнт и прежний индекс восстановлены в `downgrade`.
- **Проверено, а не предположено:** `alembic upgrade head` на пустой базе → `alembic check` без
  замечаний; `downgrade 0011` возвращает ровно вид 0009 (констрейнт + неуникальный индекс),
  повторный `upgrade head` снова сходится; строки `dev_applications` пересборку таблицы
  переживают; внешний ключ на `students` и уникальность `student_id` после миграции живы.
- **Регрессия под тестом:** `tests/test_migrations.py` поднимает пустую базу всей цепочкой и
  сверяет её с `Base.metadata` через `compare_metadata`. Без 0012 тест падает — проверено
  откатом файла миграции. Это единственная проверка, которая видит расхождение миграций с
  моделями: на уже собранной базе его не видно.

## Стенд для жюри на Render (15.10.2026)

Демонстрация переезжает на Render: жюри хакатона получает ссылку, входит по выданным логину
и паролю и само проходит QR-регистрацию вторым учеником. Готовятся к этому две вещи —
демонстрационные данные (потому что база на бесплатном тарифе живёт до первого перезапуска)
и то, как приложение запускается на чужой платформе. Что и как заведено на Render —
в `docs/DEPLOY.md`, здесь решения.

**База и заливка**

- **У заливки одна точка входа — `seed_all`**, её зовут и `scripts/seed_demo.py` (для
  человека), и приложение на старте (`_seed_demo_at_startup`). Иначе демонстрация на стенде
  и демонстрация на ноутбуке разъезжаются: две копии кода заливки — это две разные школы.
- **`seed_all` коммитит сам.** `SessionLocal` создан без «подтвердить при выходе из `with`»
  (`autoflush=False, autocommit=False`), поэтому коммит внутри вызывающего `with`-блока
  закрывался откатом: заливка на старте была бы видна ровно до конца запроса. Тот, кто зовёт,
  только закрывает сессию.
- **Заливка на старте срабатывает только на пустой базе** и только при `SEED_DEMO=1`.
  «Заполнить при запуске» не должно уметь стереть живой сайт. Повторный запуск ничего не
  дублирует: у каждой таблицы свой естественный ключ. Учителя и критерии заливаются тем же
  `seed_all`, но по своему условию (пустая таблица учителей или критериев), и берут данные
  из `TEACHERS_DATA_FILE` с откатом на `data/teachers.demo.json` — настоящих ФИО на стенде нет.
- **Демонстрация — 29 учеников** по классам 8А, 8Б, 9А, 9Б, 10А, 10Б, с именами, придуманными
  заново: посты с лайками и комментариями, отзывы об учителях, уроки и домашние задания
  каждому классу, три жалобы в очереди модерации. Пустые «Уроки» и «Мой класс» на стенде
  выглядят как поломка, а не как скромная демонстрация.
- **29 учеников — не круглое число, и это нарочно.** Аккаунт жюри (`JURY_LOGIN`) — тридцатый,
  ровно `OPEN_REGISTRATION_LIMIT`. Пока порог не взят, на стенде открыта обычная почтовая
  регистрация, и жюри могло бы завести себе аккаунт само, мимо QR. Теперь
  `registration_open()` возвращает `False`, `/register` уводит на `/register/qr`, и остаётся
  ровно тот сценарий, который показываем.
- **Аккаунты жюри создаются только из переменных окружения** (`JURY_LOGIN`/`JURY_PASSWORD`,
  `JURY_ADMIN_LOGIN`/`JURY_ADMIN_PASSWORD`). Пара не задана — аккаунта нет вовсе: пароля по
  умолчанию у стенда быть не должно. В базе остаются только хеши argon2, в git — ничего.

**Одно устройство у жюри**

- **Под QR-кодом лежит та же регистрация ссылкой** (`/scan?payload=…`) и кнопка
  «Скопировать ссылку»: телефон один, а окон нужно два — окно новичка с кодом и второе окно
  (приватное), где жюри уже вошло учеником и подтверждает код. Ссылка абсолютная, и при
  `COOKIE_SECURE=true` строится **с https нарочно**: http-ссылка не донесла бы куку сессии до
  второго окна, и подтверждение молча не находило бы ученика.
- **Страница сканера без камеры.** `/scan?payload=…` подставляет код в ту же форму, что и
  камера, и не просит доступ к камере; распознавание по-прежнему через `getUserMedia`, но оно
  теперь необязательное. Срок жизни кода и «срабатывает один раз» не меняются.

**Потолки на закрытом сайте**

- **Ограничение — это приглашение, а не защита от чужих.** Пока сайт закрыт, единственный
  вход — QR, поэтому потолок аккаунтов равен потолку самого сайта: 3 подтверждения на ученика
  за скользящие сутки (`QR_INVITES_PER_STUDENT`, `QR_INVITE_WINDOW_HOURS`) и 40 аккаунтов,
  созданных через QR, на весь стенд (`QR_ACCOUNT_LIMIT`).
- **Потолки проверяются в самих запросах, а не до них:** `INSERT … SELECT … WHERE
  (SELECT COUNT(…) FROM …) < limit` и `UPDATE … WHERE … < limit`. Проверка «прочитал —
  посчитал — записал» на SQLite разъезжается под одновременными запросами; в этом же
  репозитории так уже сделан почтовый лимит. Отказы различаются: исчерпан личный лимит и
  исчерпан общий потолок — это разные фразы.
- **`purge_expired_tokens` больше не трогает `used`-токены.** Счётчик созданных аккаунтов
  считается по подтверждённым токенам, и если чистить их как просроченные, потолок каждые
  сутки открывался бы заново — то есть не ограничивал бы ничего.
- **У ассистента к личному лимиту добавился суточный на весь сайт**
  (`ASSISTANT_DAILY_LIMIT`, 200): вопрос, дошедший до модели, стоит денег, и по одному ученику
  этого не видно. Отказ — понятная фраза и `Retry-After`, не «ошибка сервера».

**Запуск**

- **Ровно один рабочий процесс uvicorn.** Ограничители частоты считаются в памяти процесса
  (`app/services/rate_limit.py`), поэтому второй воркер удвоил бы каждый лимит, а не ускорил
  сайт. По той же причине лимиты сбрасываются при перезапуске сервиса.
- **Команда запуска — `alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port
  $PORT --workers 1`;** порт назначает платформа, и `0.0.0.0` — не вкусовщина: сервис на
  `127.0.0.1` снаружи не виден, и проверка здоровья не находит его.
- **`/healthz` отвечает `ok` без базы и без входа** — проверке здоровья платформы нечего
  делать в нашей схеме, а страница, которой нужна сессия, уронила бы деплой при живом сайте.
- **Секреты только из окружения**, значений по умолчанию в коде нет: `SECRET_KEY`
  Render генерирует сам, ключ ассистента приходит переменной и, если его нет, ассистент
  отвечает по таблицам школы. Пути — от корня проекта (`_absolute`), а не от текущего
  каталога: платформа запускает команду не оттуда, откуда запускаю я.
- Дальше — сам деплой: создать сервис по `render.yaml`, прогнать сценарий жюри на живой
  ссылке. Этап 14 (безопасность) переносится после него.

**Адрес модели стал настройкой**

Идентификаторы моделей у провайдеров настраивались и раньше (`*_MODEL`), а адреса были
вписаны в `app/services/assistant.py` константами — на стенде это лишний повод пересобирать
образ ради смены провайдера или прокси. Теперь и адрес — настройка: `ANTHROPIC_BASE_URL`,
`OPENAI_BASE_URL`, `DEEPSEEK_BASE_URL`, со боевыми адресами провайдеров в качестве значений
по умолчанию. В переменной лежит **корень API**, путь к методу дописывает `_endpoint`
(`/messages` у Anthropic, `/chat/completions` у OpenAI и DeepSeek): иначе «то же самое, но
без `/v1`» превращалось бы в ручную склейку URL в чужой переменной. Пустой корень — это
незаполненная настройка, а не адрес `/chat/completions`: запрос не уходит, ассистент
отвечает той же честной фразой, что и при упавшей модели.

`render.yaml` переведён на DeepSeek — это тот провайдер, с которым стенд и пойдёт
(`DEEPSEEK_API_KEY` спрашивают при создании сервиса, `DEEPSEEK_MODEL` и `DEEPSEEK_BASE_URL`
заданы значениями, чтобы на панели было видно, куда сайт ходит). Порядок выбора провайдера
не менялся и остался «первый заполненный ключ побеждает»: Anthropic, затем OpenAI, затем
DeepSeek. Личный лимит и суточный потолок ассистента не трогали — они про деньги, а не про
провайдера.

## Заметки о процессе

- Обычные этапы (S и M) делаю сам, напрямую. Цепочка `planner → coder → reviewer`
  (`.claude/agents/`) включается только для этапа 12 и финальной проверки безопасности —
  см. «Правило исполнения».
- Субагенты не делают git-коммитов — коммиты делает человек или основной агент после проверки.
- Каждый этап проверяется вручную на живом сервере: миграции (upgrade/downgrade/`alembic check`),
  доступ без сессии, бан, экранирование HTML, поведение при неверных данных.
- Автотесты — `pytest`; запускать `.venv/bin/python -m pytest tests`. Покрыты фильтр ПДн,
  rate limit, лимит попыток входа, CSRF, security-заголовки, публикация постов с
  комментариями (сквозные, через HTTP и с проверкой строк в БД) и вся админка модерации —
  включая сверку списка маршрутов с тестовой таблицей, чтобы новый экран не мог появиться
  без проверок доступа и CSRF.
