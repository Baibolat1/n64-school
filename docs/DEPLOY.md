# Демонстрационный стенд на Render

Стенд нужен ровно для одного: дать жюри хакатона ссылку, по которой открывается живой
сайт с наполненной школой. Всё, что для этого нужно, лежит в репозитории
(`render.yaml`), а секреты — в переменных окружения сервиса: в git их нет.

Стенд — **одна школа и один процесс**. Ограничители частоты считаются в памяти процесса
(`app/services/rate_limit.py`), поэтому рабочих процессов у uvicorn ровно один: второй
удвоил бы каждый лимит. По той же причине на бесплатном тарифе Render база живёт во
временной файловой системе и пропадает при перезапуске — стенд заливает её заново на
старте (см. «Что происходит при старте»).

## Переменные окружения

| Переменная | Зачем | Значение на стенде |
| --- | --- | --- |
| `SECRET_KEY` | Подписывает сессии учеников, куки QR-кода и хеши токенов | Render генерирует сам (`generateValue: true`); **в коде значения по умолчанию нет**, без него приложение только предупреждает в журнале |
| `COOKIE_SECURE` | Куки сессий уходят только по HTTPS | `true`. На стенде только так: Render отдаёт сайт по HTTPS, а http-ссылка не смогла бы донести куку сессии до второго окна |
| `SEED_DEMO` | Залить демонстрацию при старте, если база пуста | `1` |
| `DATABASE_PATH` | Файл SQLite | `school.db` (относительный путь считается от корня проекта, а не от текущего каталога) |
| `DEBUG` | Режим отладки | `false` |
| `JURY_LOGIN` | Почта ученика для жюри (класс 8А) | задаётся при создании сервиса, в git не попадает |
| `JURY_PASSWORD` | Пароль этого ученика | то же |
| `JURY_ADMIN_LOGIN` | Логин админа для экранов модерации | то же |
| `JURY_ADMIN_PASSWORD` | Пароль этого админа | то же |
| `ANTHROPIC_API_KEY` | Ключ ассистента (необязательно) | пусто — ассистент отвечает по таблицам школы и честно говорит «не знаю»; ключ можно вписать позже |

`JURY_*` — это **не** данные демонстрации: их задаёт тот, кто создаёт сервис, а в базе
остаются только хеши (argon2). Если пару логин-пароль не заполнить, аккаунт не создаётся
вовсе — «пароля по умолчанию» у стенда нет.

## Создание сервиса

1. Render → **New** → **Blueprint** → выбрать репозиторий. Файл `render.yaml` в корне
   описывает сервис `n64hub-demo`: сборку, команду запуска, проверку здоровья и
   переменные. Render покажет список переменных и спросит значения для тех, что помечены
   `sync: false` — это `JURY_LOGIN`, `JURY_PASSWORD`, `JURY_ADMIN_LOGIN`,
   `JURY_ADMIN_PASSWORD` и `ANTHROPIC_API_KEY` (последний можно оставить пустым).
2. **Create**. Первая сборка — `pip install -r requirements.txt`, первые запуск —
   `alembic upgrade head` и uvicorn (см. ниже).
3. Дождаться перехода сервиса в **Live** и проверить `https://<имя>.onrender.com/healthz`
   — он обязан ответить `ok` без базы и без входа. Если проверка здоровья не проходит,
   дело почти наверняка в порту: сервис должен слушать `$PORT` на `0.0.0.0`, и это делает
   команда запуска из `render.yaml`.

Без Blueprint то же самое заводится руками: **New** → **Web Service**, сборка
`pip install -r requirements.txt`, запуск
`alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT --workers 1`,
проверка здоровья `/healthz`, переменные — из таблицы выше.

## Что происходит при старте

```
alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT --workers 1
```

- `alembic upgrade head` — обязателен: у свежего сервиса база пустая, а без схемы каждая
  страница отвечает 500.
- `--host 0.0.0.0 --port $PORT` — порт назначает платформа, и он же её единственная
  примета, что сервис поднялся. Собственный порт по умолчанию (`127.0.0.1:8000`) снаружи
  не виден, и проверка здоровья такого сервиса не находит.
- `--workers 1` — ограничители частоты живут в памяти процесса (см. выше).
- Заливка (`app.main._seed_demo_at_startup`) срабатывает, **только если в базе нет ни
  одного ученика**, и только при `SEED_DEMO=1`. База, в которой уже что-то есть, не
  трогается: «заливка при старте» не должна уметь стирать живой сайт. Повторный запуск
  ничего не дублирует — у каждой таблицы свой естественный ключ.
- Файловая система бесплатного тарифа временная: после перезапуска база пустая, и стенд
  заливает демонстрацию заново, вместе с аккаунтами жюри. Данные, которые жюри создаст в
  прошлый заход, тоже пропадут — так и задумано.

## Сценарий жюри

1. **Войди по логину.** `/login` → вкладка «Почта и пароль» → `JURY_LOGIN` и
   `JURY_PASSWORD`. Ученик попадает в 8А: в ленте посты с лайками и комментариями, в
   «Расписании» — неделя класса и домашние задания, в «Моём классе» — одноклассники.
2. **Открой QR.** `/register/qr` — это страница *новичка*: она просит почту и показывает
   код, которым регистрацию подтверждает действующий ученик. То же самое делает `/register`,
   если почтовая регистрация уже закрыта (в демонстрации учеников ровно
   `OPEN_REGISTRATION_LIMIT`, то есть тридцать, — она закрыта).
3. **Открой ссылку в приватном окне и зарегистрируйся.** Под QR-кодом лежит та же
   регистрация **ссылкой** и кнопка «Скопировать ссылку» — для одного устройства и двух
   окон. Открыть ссылку нужно в приватном окне и войдя там **другим** учеником (например,
   тем же аккаунтом жюри): окно новичка остаётся в обычном. Страница сканера получит код и
   подтвердит его без камеры, а окно новичка попросит пароль и пустит нового ученика.
   Код живёт 24 часа и срабатывает один раз.
4. **Посмотри ленту, лайки, отзывы, жалобы.** Лайк — сердце на карточке, комментарий —
   поле под постом. Отзывы об учителях: `/teachers` (имена в демонстрации выдуманы).
   Жалоба — «…» на карточке поста; очередь жалоб видит админ:
   `/admin/login` с `JURY_ADMIN_LOGIN` и `JURY_ADMIN_PASSWORD`, дальше `/admin/reports` —
   в демонстрации там три жалобы, их можно разобрать, отклонить или скрыть содержимое.
   Ассистент — `/assistant`: он отвечает по таблицам школы, а модель спрашивает только о
   том, чего в них нет.

## Ограничения, о которых стоит знать на стенде

- Приглашения через QR: **3 подтверждения на ученика за 24 часа** и **40 аккаунтов за всю
  жизнь стенда** (`QR_INVITES_PER_STUDENT`, `QR_ACCOUNT_LIMIT`). Это защита, а не поломка:
  иначе один ученик наполнил бы закрытый сайт в одиночку.
- Почтовая регистрация: закрыта при 30 учениках (в демонстрации ровно столько), остаётся
  QR-код и пригласительные коды из админки.
- Ассистент: **20 вопросов в час на ученика** и **200 в сутки на весь сайт**
  (`RATE_LIMIT_ASSISTANT`, `ASSISTANT_DAILY_LIMIT`). При исчерпании — понятная фраза на
  странице, а не ошибка сервера.
- Ограничители сбрасываются при перезапуске сервиса: они в памяти процесса.

## Локальная проверка стенда

Тот же запуск, что и на Render, но на своей машине (порт 10000 — из команды в `render.yaml`):

```bash
DATABASE_URL=sqlite:////tmp/stand.db SEED_DEMO=1 PORT=10000 \
  JURY_LOGIN=jury@example.com JURY_PASSWORD='...' \
  JURY_ADMIN_LOGIN=jury-admin JURY_ADMIN_PASSWORD='...' \
  .venv/bin/python -m app
```

Если в `.env` лежит `DATABASE_URL`, он перебивает `DATABASE_PATH`: для локальных опытов
удобнее задать именно `DATABASE_URL` (как выше), а не путь к файлу.

## Если что-то не так

| Симптом | Причина |
| --- | --- |
| Проверка здоровья не проходит, деплой не переходит в Live | Сервис не слушает `$PORT`/`0.0.0.0` — смотреть `startCommand` |
| Все страницы отвечают 500, `/healthz` — `ok` | Не прошли миграции: схема пустая. Смотреть журнал сборки и запуска |
| Сайт пустой: лента, расписание пусты | Заливка пропущена — `SEED_DEMO` не равен `1`, либо в базе уже были ученики |
| Аккаунтов жюри нет | Не задана пара `JURY_LOGIN`/`JURY_PASSWORD` (или `JURY_ADMIN_*`) — аккаунт без неё не создаётся |
| Жюри вошло, а ленту не видит | Второе окно открыто по `http://` при `COOKIE_SECURE=true`: куку сессии браузер туда не отдаёт |
| Страница сканера просит камеру | Открыт `/scan` без кода: ссылку копируют со страницы QR (кнопкой «Скопировать ссылку») |
